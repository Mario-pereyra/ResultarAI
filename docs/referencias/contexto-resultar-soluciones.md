Se establece un congelamiento completo (_code freeze_) de código y parámetros en PRD 48 horas antes de cualquier salida en vivo (_go-live_).

* **6.2. Criterios de Calidad en el Ambiente Intermedio (BIB):** El ambiente de biblioteca y calidad (BIB) debe sustentarse sobre una base de datos que corresponda a una copia refrescada exacta de PRD o, en su defecto, incorporar una masa de datos altamente representativa del negocio, actualizada de forma quincenal o bajo demanda según los requerimientos de las pruebas de certificación. Antes de autorizar la liberación de un paquete hacia el ambiente de producción, se exige de forma obligatoria la ejecución exitosa de pruebas de regresión funcional, validación de integraciones entre módulos nativos de TOTVS, verificación de endpoints externos y contar con el documento UAT (_User Acceptance Testing_) firmado y aprobado por el cliente o la consultora funcional.

### 7. Infraestructura de Servidores y Despliegue del ERP

* **7.1. Configuración del Servidor del Cliente (IPs Dedicadas y Windows Server):** Cada infraestructura implementada opera de forma aislada en el servidor físico o virtual del cliente. Al adquirir el ERP, se le asigna una dirección IP pública/privada dedicada y exclusiva a su servidor corporativo. * **7.2. La Capa de Procesamiento (AppServer y Repositorio RPO):** El núcleo de procesamiento de Protheus reside en el componente ejecutable **AppServer** (Servidor de Aplicaciones). Este binario es el encargado de procesar la lógica de negocio del ERP, administrando las sesiones de los usuarios que se conectan a la plataforma de **Protheus Web** (SmartClient HTML). El AppServer aloja internamente el archivo compilado denominado **RPO (Repositorio de Objetos)**, el cual concentra la totalidad de las funciones de la marca, las rutinas del estándar de TOTVS y las personalizaciones customizadas desarrolladas por la fábrica de software.

* **7.3. La Capa de Conectividad Intermedia (TOTVS DBAccess):** Protheus no interactúa directamente con los motores relacionales de bases de datos. Arquitectónicamente, se implementa de manera mandatoria el middleware **TOTVS DBAccess**. Este componente actúa como un motor avanzado de conectividad intermedio encargado de recibir las consultas nativas del AppServer, traducirlas de forma transparente, gestionar los cursores de base de datos y administrar el pool de conexiones seguras hacia el servidor relacional.

* **7.4. El Almacenamiento Relacional (Microsoft SQL Server):** El almacenamiento físico de los datos estructurados, registros históricos de transacciones y los diccionarios de control del ERP está estandarizado bajo el motor de base de datos relacional **Microsoft SQL Server (MS SQL)**, cuyas tareas de optimización de índices y ejecución periódica de backups de seguridad de bases de datos son administradas por el área de infraestructura técnica.

### 8. Arquitectura del Entorno de Desarrollo y Estándares de Código

* **8.1. Configuración del IDE (VS Code y Extensión Oficial TDS):** El entorno estandarizado de programación para la totalidad del equipo técnico (Seniors, Semi-Seniors y Juniors/Fábrica) es el editor **Visual Studio Code (VS Code)**. La interacción con el AppServer y la base de código del ERP se realiza exclusivamente mediante la instalación de la extensión oficial de la marca: **TDS (TOTVS Developer Studio) para VS Code**. A través de este entorno, los desarrolladores se conectan de forma remota a los AppServers de los clientes en sus respectivos ambientes autorizados (DES) para ejecutar tareas de depuración en caliente (_debugging_), compilación de parches de actualización y compilación de archivos de código fuente generales. Para las interacciones con el servidor MS SQL, los desarrolladores instalan extensiones dedicadas directamente en el IDE o utilizan manejadores de bases de datos independientes.

* **8.2. El Estándar de Documentación Interna Naciendo de Fábrica (Protheus Doc):** Como política mandatoria de control de calidad de software y buena práctica técnica, todo archivo de código fuente personalizado (`.prw`, `.tlpp`, `.ch`) generado por la fábrica de software debe nacer estructurado bajo la sintaxis oficial de **Protheus Doc**. El desarrollador debe colocar de forma obligatoria el bloque de documentación estructurado de la siguiente manera, inmediatamente antes de la definición de cada función, clase o método personalizado:

  Fragmento de código

  ```
  /*/{Protheus.doc} u_NomFuncion
  Descripción detallada de la rutina y su impacto operativo en el ERP.
  @author  Fábrica de Software (Junior / Desarrollador)
  @since   07/07/2026
  @version Protheus 12
  @param   param1, Tipo, Descripción del parámetro de entrada.

  ```

  La inserción estricta de este bloque de metadatos permite que el compilador de la extensión TDS procese el mapa de la función, habilitando el autocompletado inteligente de código y la visualización de ayuda técnica flotante (_tooltips_ informativas) dentro de VS Code para optimizar la productividad y el mantenimiento del software por todo el equipo técnico.

### 10. Mapeo de la Base de Datos y Diccionarios de Protheus

* **10.1. El Corazón del Sistema: Las Tablas Metadato (SX1 a SX10 y SIX):** Protheus se caracteriza por ser un sistema orientado por datos; la estructura de sus pantallas, campos, validaciones y comportamiento no está cableada rígidamente en el código, sino que es leída dinámicamente desde un conjunto de tablas del sistema denominadas "Tablas SX" o metadatos, las cuales se estructuran de la siguiente manera:

  * **SIX:** Tabla de control técnico encargada de la definición, estructura y ordenamiento de los Índices del sistema.

  * **SX1:** Configuración de Preguntas dinámicas de las rutinas y reportes (_Perguntas_).

  * **SX2:** Registro maestro y catálogo de Archivos / Tablas oficiales del ERP.

  * **SX3:** Diccionario maestro de Campos (longitudes, tipos, textos, propiedades y funciones de validación).

  * **SX4:** Estructura física de los índices en el motor relacional.

  * **SX5:** Almacenamiento de Tablas Genéricas del sistema (códigos de tablas internas).

  * **SX6:** Catálogo de Parámetros globales del ERP (variables de configuración del sistema).

  * **SX7:** Registro de Gatillos automáticos de campos (_Gatilhos_).

  * **SX8:** Tabla de control para la generación de numeraciones correlativas automáticas y bloqueos de registros.

  * **SX9:** Diccionario de Relaciones lógicas e integridad referencial entre tablas.

  * **SX10:** Historiales de modificaciones y definiciones adicionales extendidas de campos.

* **10.2. Lógica de Negocio Relacional: Encabezados e Ítems (Ejemplo SC5 y SC6):** El volumen masivo de datos transaccionales de las empresas opera sobre tablas de negocio. Estas tablas guardan comúnmente una estricta relación jerárquica de dependencia dividida en dos componentes físicos: **Encabezado e Ítems**.

  * _Ejemplo Maestro del Proceso de Ventas:_ El ERP modela los pedidos comerciales utilizando la tabla **SC5** como el Encabezado del Pedido de Venta (concentrando datos únicos como cliente, fecha de emisión, condición de pago y totales), vinculada relacionalmente en una estructura de uno a muchos con la tabla **SC6**, la cual almacena detalladamente los Ítems de los Pedidos de Venta (concentrando productos, cantidades, precios unitarios y descuentos por cada línea del pedido).

### 11. Control de Integridad y Mitigación de Inconsistencias

* **11.1. Los Campos Críticos de Control del Motor (R\_E\_C\_N\_O\_ y D\_E\_L\_E\_T\_):** El motor relacional MS SQL Server actúa estrictamente como un repositorio físico de filas, ya que el control lógico de los registros es administrado de forma interna por Protheus mediante el uso obligatorio de dos campos de control nativos presentes en la totalidad de las tablas de negocio:

  * **`R_E_C_N_O_` (Record Number):** Es el identificador numérico secuencial único de la fila. Este valor consecutivo no es un campo `IDENTITY` automático de SQL Server, sino que es controlado y asignado estrictamente por el binario de Protheus en coordinación con la tabla de control del sistema `SX8`. Ejecutar una inserción directa por fuera del sistema alterando la secuencia de este contador corrompe el consecutivo, provocando el bloqueo inmediato de futuras inserciones de datos desde las pantallas del ERP.

  * **`D_E_L_E_T_` (Borrado Lógico):** Protheus no ejecuta eliminaciones físicas de registros (_hard delete_) bajo operaciones estándar de usuario. Cuando un registro es borrado desde la interfaz web, el sistema aplica un borrado lógico (_soft delete_) marcando el campo `D_E_L_E_T_` con el carácter asterisco (`*`). Las filas activas y válidas para el negocio se mantienen con dicho campo completamente vacío (espacio en blanco). Romper esta lógica mediante borrados físicos en el motor destruye la integridad referencial histórica del sistema.

* **11.2. Matriz de Soluciones Autorizadas por Niveles (Interfaces vs. APSDU vs. MsExecAuto):** Con el objetivo fundamental de erradicar descalces de datos, bypass de validaciones funcionales lógicas o corrucciones en el servidor de aplicaciones debido a la sincronización de buffers en memoria, se establece el manual estricto de mitigación de inconsistencias, el cual prohíbe el uso de scripts de SQL crudo (`UPDATE`, `INSERT`, `DELETE`) en tareas ordinarias y obliga a la fábrica a operar bajo tres niveles de solución técnica autorizados:

  * **Nivel 1: Uso de Interfaces Nativas (SIGAMDI / SIGACFG):** Cualquier modificación de variables, actualización de parámetros maestros, alteración de propiedades de campos o edición de preguntas debe ser realizada de forma exclusiva a través de los formularios y pantallas del módulo configurador. Esto garantiza que las tablas metadato `SX` del sistema sufran actualizaciones en bloque homogéneas y coordinadas.

  * **Nivel 2: Uso Controlado de la Herramienta APSDU:** En escenarios específicos de soporte técnico avanzado donde sea mandatorio corregir un registro transaccional corrupto de negocio (por ejemplo, un campo mal grabado en las líneas de ítems de la tabla `SC6`), queda prohibido abrir la tabla desde SQL Management Studio. Se debe invocar obligatoriamente la utilidad nativa de administración **APSDU** (_Advanced Protheus System Data Utility_). Al pasar directamente a través del middleware DBAccess, la utilidad lee el mapa de diccionarios de la base de datos, respeta la estructura de campos y mitiga el riesgo de corromper los punteros de los índices físicos o generar bloqueos huérfanos de registros.

  * **Nivel 3: Manipulación Masiva mediante Programación (MsExecAuto):** Cuando se requiera realizar la inserción, modificación o procesamiento masivo de un volumen considerable de datos de negocio (como el procesamiento masivo de pedidos de venta en las estructuras de las tablas comerciales `SC5` y `SC6`), queda estrictamente prohibido el diseño de rutinas basadas en comandos de inserción directa de bases de datos. El desarrollador de la fábrica debe programar de forma obligatoria una rutina automatizada en VS Code invocando la funcionalidad **ExecAuto (MsExecAuto)** provista por la arquitectura de la rutina estándar correspondiente. Esta buena práctica obliga al AppServer a simular por completo y de forma transparente el comportamiento de un usuario interactuando frente a la pantalla web, forzando la ejecución automática del 100% de las reglas de negocio, gatillos automáticos (`SX7`) y validaciones lógicas del diccionario (`SX3`, `X3VALID`) antes de plasmar físicamente las filas dentro del motor relacional MS SQL Server.

### 12. Desarrollo e Integración con API REST

* **12.1. Paradigmas de Programación (AdvPL Tradicional vs. Modernización con TLPP):** La fábrica de software implementa el desarrollo de servicios web bajo la arquitectura REST, la cual convive bajo dos metodologías de programación en el RPO:

  * **AdvPL Tradicional:** Utiliza la declaración de clases del tipo `WSRESTFUL` y la definición de métodos específicos para capturar de forma manual parámetros pasados por cadena de URL (vía arreglos de propiedades del tipo `Self:aParam`) o ejecutar la decodificación de datos del cuerpo del mensaje mediante comandos nativos del tipo `Self:GetContent()`.

  * **Modernización con TLPP:** Es la arquitectura moderna e institucional bajo lenguaje _TOTVS Language Plus Plus_ (`tlppCore`). Permite agilizar el desarrollo mediante la implementación de **Annotations** nativas del compilador para mapear directamente las rutas de los endpoints y los verbos HTTP correspondientes (ej. `@Get("/api/v1/pedidos")`, `@Post("/api/v1/clientes")`), autorizando tipado fuerte de variables, control estricto de namespaces orientados a objetos y bloques avanzados `try...catch` para la captura limpia de excepciones de ejecución en el AppServer.

* **12.2. Flujos de Datos Intercambiados (Exposición y Consumo JSON):** Toda transferencia de información entrante o saliente procesada a través del entorno de servicios web se gestiona de manera unificada mediante la serialización, parsing y desestructuración lógica de objetos estructurados en formato **JSON**.

* **12.3. Escenarios de Uso Comunes en la Comunidad de Partners:** Las arquitecturas de API REST desarrolladas e implementadas por la comunidad de partners de TOTVS se enfocan en resolver integraciones comerciales de alta complejidad:

  * _Sistemas E-commerce:_ Conexión directa con portales transaccionales externos (como VTEX o Magento), donde Protheus expone endpoints para recibir payloads JSON con las compras de la web e inyectar de forma automática los registros comerciales en las tablas transaccionales de pedidos (`SC5` y `SC6`).

  * _Sistemas CRM y Webhooks:_ Conexión bidirecional automatizada para la sincronización de altas de clientes y prospectos.

  * _Automatización de Mensajería (Chatbots / WhatsApp):_ Consumo y exposición de APIs REST para la consulta de stocks o estados de despachos mediante bots interactivos externos.

  * _Orquestadores RPA:_ Conexión segura para plataformas de software de automatización robótica de procesos que interactúan con las reglas de negocio de Protheus.

* **12.4. Consideraciones Técnicas para el Desarrollo de API REST en Protheus:**

  * **Mapeo Obligatorio hacia MsExecAuto:** Al codificar métodos del tipo `POST` o `PUT` destinados a la recepción de datos masivos orientados a lógica de negocio, se prohíbe de forma absoluta la escritura directa de filas mediante bloques lógicos manuales del programador. Los datos JSON parseados por el endpoint deben ser mapeados a un array estructurado y direccionados directamente hacia la rutina automática **MsExecAuto** correspondiente. Esto asegura que el AppServer fuerce la validación del diccionario antes de realizar la inserción de las líneas en la base de datos relacional.

  * **Salidas de Errores Técnicos para Debugging:** En el desarrollo de métodos orientados al control de excepciones o fallas del servidor (códigos HTTP de error `500`), es mandatorio estructurar una respuesta JSON limpia capturando dinámicamente el mensaje de error del compilador o la excepción interna devuelta por el AppServer o el RPO. Esta práctica técnica le permite al equipo técnico de la fábrica (Juniors) identificar el origen exacto de la falla del compilado sin necesidad de inspeccionar directamente las trazas físicas del servidor del cliente.

  * **Compilación y Documentación vía REST-DOC:** Al desarrollar APIs bajo la arquitectura moderna de TLPP, el desarrollador debe incluir la sintaxis nativa de comentarios de documentación técnica dentro de la estructura de código. El motor interno de Protheus compila estas etiquetas y expone de forma automática un portal web auto-generado de documentación interactiva (estilo Swagger/OpenAPI), facilitando el entendimiento de las estructuras de parámetros de entrada y salida sin necesidad de abrir los archivos de código fuente físicos `.tlpp` o `.prw`.

### 13. Tecnologías Adyacentes y Paradigmas Modernos de Protheus

* **13.1. Interfaces Web Modernas con Framework PO-UI (Angular):** Corresponde al framework de frontend e interfaz de usuario de código abierto basado en **Angular**, desarrollado y mantenido oficialmente por TOTVS. Se establece como el estándar actual de la marca para la construcción de portales web a medida, aplicaciones personalizadas avanzadas y dashboards interactivos visuales. Estos componentes corren de forma externa e independiente a la interfaz clásica de SIGAMDI, consumiendo los datos expuestos por el ERP de manera ágil a través de llamadas a servicios API REST.

* **13.2. El Patrón de Arquitectura MVC en Protheus:** Metodología y patrón de programación orientado a objetos de uso mandatorio para el diseño y desarrollo de cualquier rutina personalizada o pantalla nueva en el ERP. Separa estructuralmente la capa de datos, propiedades y validaciones lógicas del diccionario (**Model** - estructurado mediante clases como `FWFormStructure`), la interfaz de visualización en pantalla (**View**) y las acciones lógicas de control del comportamiento de la rutina (**Controller** - estructurado mediante clases de interfaz como `FWMBrowse`). Su adopción reduce la codificación manual al permitir que el framework de TOTVS administre de forma nativa la renderización y validación del diccionario de datos.

* **13.3. Consultas Optimizadas vía Embedded SQL (SQL Incrustado):** Funcionalidad técnica avanzada disponible en AdvPL y TLPP que le permite al programador incrustar sentencias y queries SQL puras y nativas directamente dentro de bloques delimitados en el código mediante la sintaxis:

  Fragmento de código

  ```
  BeginSQL ... EndSQL
  ```

  Esta tecnología reemplaza la antigua concatenación manual de cadenas de texto y el uso confuso del componente `TCQuery`. El compilador técnico de Protheus optimiza estas consultas de forma automática y transparente a nivel del middleware DBAccess, incrementando la velocidad de ejecución, agilizando el procesamiento de grandes volúmenes de datos en SQL Server y blindando al sistema contra ataques de inyección de código SQL.

* **13.4. Análisis Predictivo con Inteligencia Artificial (TOTVS Carol):** Plataforma institucional de Big Data y gestión de Inteligencia Artificial de TOTVS. Posee la capacidad técnica de conectarse y absorber los registros históricos alojados en las tablas de negocio de Protheus para aplicar algoritmos avanzados de _Machine Learning_. Su implementación está enfocada en proveer capacidades de analítica predictiva de alta demanda para sectores industriales o agropecuarios de la cartera de clientes de la empresa (tales como modelos predictivos de comportamiento ganadero, estimación de demandas de insumos o análisis predictivo de riesgos financieros de mercado).
