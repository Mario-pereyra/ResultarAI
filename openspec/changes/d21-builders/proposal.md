## Why

Hasta acá, crear o cambiar un Agent Manifest o un paquete de Skill exige tocar YAML a mano y abrir un PR: no hay manera de que un Admin cree un agente nuevo, ajuste su toolset o publique una Skill sin pasar por Git, y no existe ningún camino para que un Técnico proponga algo o para que cualquier empleado pruebe una idea sin escrituras. `design/FUNCIONALIDADES.md` §13 y `design/VISTAS/09-builders.md` (vistas 41 y 42) fijan ese camino: dos builders solo-Admin que producen versiones inmutables de agente y de skill sin romper ninguna regla dura (prefijo cache-safe estático, toolset horneado por versión, tools solo vía skill). Como el runner de evals real (`e25-evals-gates`) lo ejecuta el product owner al final, el gate de publicación de estos builders nace **pluggable en modo placeholder** (`docs/07-roadmap.md`, Nota de desacople), reutilizando el mismo contrato que ya define `d20-gobernanza-plataforma` para el Registro de Prompts.

## What Changes

- Se implementa el **Agent Builder** (vista 41, solo Admin): wizard que produce/edita una versión de `AgentManifest` (`a02`) junto con su versión de prompt vinculada en el Registro de Prompts (`d20`) — el paso "Prompt" reutiliza el ciclo `draft → published → retired` de `d20` sin redefinirlo. El **header estático cache-safe lo antepone la plataforma**: el builder solo expone como editables las secciones posteriores al prefijo; el prefijo mismo no forma parte del payload editable. El toolset se elige exclusivamente entre Tools con `status: active` del Tool Registry (`c09`); el perfil de modelo y la escalación (`<<<NEEDS_PRO>>>`) se configuran por versión (`b05`). **Activar** una versión reutiliza el gate pluggable de publicación ya especificado en `d20` (modo placeholder: advertencia visible, no bloqueo, mientras `e25-evals-gates` no esté archivado) y, al activarse, el agente hornea su toolset y su skillset — fijos por versión, jamás recargados a mitad de sesión — y aparece en el catálogo (`d15`) conforme a la matriz de visibilidad que gobierna `d20`.
- Se implementa el **Skills Builder** (vista 42, solo Admin): wizard que produce/edita un paquete de Skill conforme a la spec oficial Agent Skills (`SKILL.md` + frontmatter válido + archivos de apoyo, `c08`) junto con su `SkillManifest` de gobernanza (`a02`), con **validación en vivo del frontmatter** (formato de `name`, `description` obligatoria, consistencia con el directorio/manifiesto). Publicar una skill exige **≥3 casos de eval declarados**: es un gate propio de conteo (no de score), distinto del gate de `d20`; los casos declarados quedan guardados como el dataset que `e25-evals-gates` ejecutará más adelante — mientras `e25` no exista, los casos NO se ejecutan (modo placeholder). Cada publicación congela una versión inmutable; editar crea una versión borrador nueva.
- Se agrega el **Registro de skills**: consulta de solo lectura (Técnico y Admin) con nombre, versión, owner y qué agentes activos la usan (derivado de `enabled_skills` de las versiones activas de `AgentManifest`).
- Se agregan las **propuestas guiadas de Técnicos**: un Técnico personaliza instrucciones dentro de un template fijo (agente o skill) con un toolset acotado a lo que su rol tiene permitido (matriz rol×tool de `d20`, consumida en solo lectura); la propuesta queda en estado pendiente y **no aparece en catálogo ni en el Registro de skills hasta que un Admin la apruebe explícitamente** (aprobación = entra al mismo flujo de borrador y gate que si la hubiera creado el Admin; rechazo notifica al Técnico con motivo vía `d12`).
- Se agrega el **sandbox self-service**: constructor no-code disponible para cualquier empleado, en un sandbox donde **nunca se ofrece una Tool de escritura** — la UI no la lista y, si se intentara igual, el Policy Gate (`a03`) la deniega por deny-by-default. Promover una construcción de sandbox al catálogo exige pasar el **mismo gate completo del Admin**, sin atajos.

## Capabilities

### New Capabilities

- `agent-builder`: wizard de creación/edición de versiones de agente (solo Admin); protección del header cache-safe puesto por la plataforma; toolset limitado a Tools activas del Tool Registry; perfil de modelo y escalación por versión; horneado fijo de toolset y skillset por versión; activación mediante el gate pluggable ya definido en `d20` (advertencia sin bloqueo en modo placeholder); aparición en catálogo tras pasar el gate.
- `skill-builder`: wizard de creación/edición de paquetes de Skill conformes a la spec Agent Skills + su Skill Manifest de gobernanza; validación en vivo de frontmatter; gate propio de publicación por conteo (≥3 casos de eval declarados, dataset para `e25-evals-gates`, sin ejecución mientras no exista); Registro de skills de consulta; propuestas guiadas de Técnicos (agentes y skills) con visibilidad condicionada a aprobación del Admin; sandbox self-service sin Tools de escritura con promoción sujeta al gate completo.

### Modified Capabilities

*(ninguna — `openspec/specs/` está vacío; ningún change previo está archivado. `d21` consume, sin redefinir, contratos ya especificados por `a02`, `a03`, `b05`, `c08`, `c09`, `d12`, `d15` y `d20`.)*

## No-objetivos

- **Sin ejecución de evals**: ni el gate de `d20` que reutiliza el Agent Builder ni el gate de conteo del Skill Builder ejecutan ni puntúan casos — eso lo aporta `e25-evals-gates`, que además reemplaza el modo placeholder por el modo enforcing cuando quede archivado. Aquí los casos de skill solo se declaran y se guardan como dataset.
- **Sin builder visual de workflows**: `design/FUNCIONALIDADES.md` §13 lo excluye explícitamente ("no hay builder visual de workflows en el alcance actual"); los workflows deterministas se definen por código + registro en `e22-workflows-deterministas`.
- **Sin skills con escritura al ERP**: la personalización Protheus (bridge, tools de escritura ERP) es Etapa P; los builders de este change no ofrecen ningún camino para crear una skill que escriba en el ERP.
- **Sin implementar el Registro de Prompts en sí** (ciclo `draft → published → retired`, diff, rollback, espejo Git, gate pluggable en sus dos modos): eso ya lo especifica `d20-gobernanza-plataforma`; el Agent Builder consume ese contrato para su paso "Prompt" y su acción "Activar", sin redefinirlo.
- **Sin la matriz de visibilidad agente×rol ni la matriz de permisos rol×tool en sí** (creación, edición, versionado, auditoría): son responsabilidad de `d20-gobernanza-plataforma`. El Paso 1 del Agent Builder y el filtrado de tools de las propuestas guiadas consumen esos contratos en lectura/escritura ya definidos por `d20`, no los reimplementan.
- **Sin kill-switch de agente/tool**: vive en `d20-gobernanza-plataforma` (feature flags); el builder no apaga agentes, solo crea/edita/activa versiones.
- **Sin cliente MCP ni ejecución real de Tools nuevas**: el toolset se selecciona desde el Tool Registry ya poblado por `c09`; este change no agrega Tools ni MCP servers.
- **Sin persistencia detallada nueva**: usa el store append-only y de auditoría de `b04-persistencia-postgres`; no se re-especifica el modelo de datos de sesiones/mensajes.

## Bounded context afectado

`scaffolding` (`docs/02-arquitectura.md`), materializado en `app/` (casos de uso de ambos builders, propuestas guiadas y sandbox: crear/editar borrador, validar paso, correr el gate propio del Skill Builder, invocar el gate de `d20` para activar una versión de agente, aprobar/rechazar propuestas, promover desde sandbox) y en `frontend/` (vistas 41 y 42, Registro de skills, propuestas guiadas y sandbox). **No se toca `core/`**: los schemas de manifiesto (`a02`), el Policy Gate (`a03`) y los ports ya existen; este change los orquesta desde casos de uso de aplicación, sin agregar dominio nuevo a `core/`.

## Impact

- `resultarai/app/builders/` (nuevo): casos de uso del Agent Builder y del Skill Builder (borrador, validación por paso, publicación/activación, propuestas guiadas, sandbox) y sus endpoints en `app/api/`.
- `resultarai/adapters/persistence_postgres/`: los borradores y versiones de `AgentManifest`/`SkillManifest` creados por los builders viven en Postgres como fuente de runtime (mismo patrón que el Registro de Prompts, `ADR-0011`); los manifiestos de fábrica (YAML en `manifests/`) siguen siendo el bootstrap y no se reemplazan. Al publicar una skill, el sistema materializa/exporta el paquete `SKILL.md` a `manifests/skills/packages/<slug>/` (espejo Git) para que el loader por filesystem de `c08` lo descubra sin cambios en `c08`.
- `frontend/`: vistas 41 (`41-builder-agentes`) y 42 (`42-builder-skills`), Registro de skills, pantallas de propuesta guiada (Técnico) y de sandbox self-service (todos los roles), bajo el shell de `d10-design-system-shell`.
- Dependencias consumidas sin redefinir: `a02-core-manifiestos` (schemas y ciclo de vida de manifiestos), `a03-core-gobernanza` (Policy Gate deny-by-default, `AuditEvent`), `b05-gateway-modelos` (perfiles de modelo, escalación por agente), `c08-agent-skills` (spec Agent Skills, loader por filesystem), `c09-mcp-tools` (Tool Registry, clasificación fija por versión), `d12-notificaciones` (notificar aprobación/rechazo de propuestas), `d15-catalogo-agentes` (contrato de visibilidad que consume el agente publicado), `d20-gobernanza-plataforma` (Registro de Prompts, gate pluggable, matrices de visibilidad y de permisos rol×tool).
- Dependencia de cierre (no bloqueante para especificar, sí para el modo enforcing): `e25-evals-gates` reemplaza el modo placeholder de ambos gates y ejecuta los casos declarados por el Skill Builder como dataset real.
- Referencia de diseño: `design/FUNCIONALIDADES.md` §13 y `design/VISTAS/09-builders.md` (vistas 41 y 42), fuentes normativas de este change.
